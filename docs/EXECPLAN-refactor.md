# ExecPlan: Deep Refactoring of OpenCanary Correlator

Status: **complete 2026-10-24** — Milestones 1–6 done; see `docs/validation.md` for the measured results behind §5 and the accepted limits that replace its former open items.
Proposed: 2026-10-24. Revised: dispatcher set confirmed (SMTP, generic webhooks, Slack, Telegram, Discord; no SMS in phase 1).

## 1. Goal

Replace the Python 2.7 / Twisted / synchronous-Redis implementation of `opencanary-correlator` with a Python 3.11+ `asyncio` service that **accepts the unmodified wire format of `opencanaryd`** (`SocketJSONHandler`: newline-delimited JSON over TCP, verified in `opencanary/logger.py` → `makePickle() = record.getMessage() + "\n"`), validates every event with Pydantic v2, keeps all correlation state in Redis via `redis.asyncio` so any number of replicas can run behind a load balancer, emits JSON audit logs with `timestamp/component/action/status/details`, and is enforced by `ruff` + strict `mypy` + `pytest`/`pytest-asyncio`.

Alert delivery is plugin-based (`BaseDispatcher`) with these channels in phase 1: **SMTP**, **generic SIEM webhook**, **Slack**, **Telegram**, **Discord**. Legacy Twisted, the deprecated `mandrill` client, `twilio==4.4.0`, `setup.py` and implicit-relative-import modules are removed. SMS is deliberately out of phase-1 scope; it is designed as a later plugin.

The legacy Redis key layout and incident field names are preserved so existing console/dashboards keep reading the same data.

**2026-10-24 — Redis topology clarified.** Removed the false “Redis Cluster-safe” claim from `docs/architecture.md`. `RedisStore.from_url()` creates a regular `redis.asyncio.Redis` client, and `save_incident()` writes an `incident:*` hash plus the `incidents` ZSET in one `MULTI`; in Redis Cluster those keys hash to different slots and the transaction fails with `CROSSSLOT`. **2026-10-24 — Ingestion performance.** Attacked the two structural costs measured in the acceptance record instead of micro-tuning. **(1) Incident lookup was O(index size):** `find_recent_incident()` read every ZSET member inside the horizon and filtered by prefix in Python, so a busy deployment re-read a growing window on every event. Added `incident-latest:<incident>:<src_host>`, a two-field hash (newest incident key + score) written atomically with the incident and validated against the horizon; a missing, stale or deleted pointer falls back to the ZSET scan, so incidents created by an older replica still merge. **(2) Events were correlated strictly one at a time:** six Redis round trips per event capped throughput at `1 / RTT`. `EventPipeline` now runs `OCC_EVENT_CONCURRENCY` lanes (default 8) sharded by CRC32 of `src_host`, sharing the `OCC_EVENT_QUEUE_SIZE` budget and `stop()` drain; one host keeps arrival order, so merging stays deterministic, while different hosts overlap. **(3) Round trips reduced from 8 to 6:** the incident write (hash + ZSET + pointer) and the lock release are now Lua scripts, which also makes the P2 release atomic in one call; `lupa` was added to the dev extra so fakeredis executes the same scripts as a real server. Measured on a real Redis 7 in a Linux container (Python 3.13, 10,000 events/100 hosts): 3.0 s before, 2.6 s with 8 lanes. The decisive case is a populated index: with 5,000 live incidents, 2,000 events took 47.9 s before and 4.6 s now. **2026-10-24 — Bounded incident history.** Closed the quadratic single-host merge left open by the performance work, where every event re-serialised the growing `events_list` CSV and `logdata` array and rewrote the whole hash. **2026-10-25 — Bounded incident lookup.** Closed the largest cost the hot-path profile found. For a source host with no `incident-latest` pointer, `find_recent_incident()` fell back to `ZREVRANGEBYSCORE incidents` and filtered every live incident in Python: 1.4 ms of residual cost with 200 live incidents and 5.5 ms with 2 000, on an otherwise constant six round trips, so ingestion was O(index size) and grew with deployment age. The scan is now bounded by `OCC_INCIDENT_LOOKUP_SCAN_LIMIT` (default 100, 1..10000) and passed to Redis as `LIMIT 0 N`, so the members beyond the cap are never transferred; the reply is newest-first, so a match inside the cap is still the newest incident for that prefix. `find_recent_incident()` returns an `IncidentLookup(key, scanned, truncated)` instead of a bare key, and the repository audits a capped miss as `incident_lookup_truncated` (warning) with `scanned`/`scan_limit` before creating a new incident — the trade-off is that a pointerless incident behind the cap produces a second incident instead of a merge, which is only reachable with state written before pointers existed or pointers deleted by an operator; walking the index to avoid it is the O(index) cost being removed. A pointer hit still scans nothing. **2026-10-25 — What the residual is.** The profile left 53 % of a hot merge unexplained and two hypotheses: the pure-Python RESP parser (`hiredis`) and `decode_responses`. `tools/profile_hot_path.py` grew a third mode, `commands`, that interleaves two calls in one loop and reports the **median of the per-iteration difference** - single-run means on this host bounce by ±30 µs, the same size as the effect being measured. Results in the Linux container (2 000 pairs, RTT ≈ 120 µs): full `HGETALL` over `HMGET` of two fields **+13.6 µs**, full `HGETALL` over `PING` +19.4 µs, `save_incident` over `PING` **+74.9 µs**, `hiredis` over the pure-Python parser **+0.4 µs** on a 5.5 KB hash read and +0.1 µs on `PING`. `hiredis` is refuted by measurement rather than intuition and stays out of the dependency set; the tool picks it up automatically if it is installed later. Decoding is below the noise floor, and the obvious `decode_responses=False` A/B is a trap because `RedisStore.hgetall()` coerces with `str()`, so the `bytes` row measures the wrapper. The `cpu` mode also gained the pure-Python half of a merge: `from_fields` 3.8 µs, `append_timestamp` + `merge_logdata` + `to_fields` 51-53 µs of which **44-46 µs is `json.loads` of the stored `logdata`**, `to_fields` alone 2.1 µs, `audit.emit` 19-21 µs. The actionable item that fell out is not on the wire at all: a capped incident decodes its whole `logdata` list on every event only to return it unchanged, so skipping that merge step when `events_truncated` is set is a behavioural no-op worth ~49 µs per hot merge. ### Strategy

The codebase is small enough for a strangler-fig rewrite rather than a line-by-line Py3 port: build the new `src/` package alongside the legacy tree, keep the legacy code untouched (so nothing is silently lost), port module-by-module with parity tests, then delete the legacy tree in one dedicated commit (Milestone 6). Each milestone is a separate commit/PR and follows TDD — tests are written first or in parallel, per AGENTS.md.

### Compatibility contract (must not change)

- **Transport**: TCP, newline-delimited UTF-8 JSON, default port `1514`; payload is exactly what `SocketJSONHandler.send()` writes. Lines with the `[ERR] '{"…"}'` prefix produced by `PyLogger.error()` are rejected with an audit record, never crash the server.
- **Event schema**: `src_host`, `src_port`, `dst_host`, `dst_port`, `logtype`, `node_id`, `local_time`, `utc_time`, `local_time_adjusted`, `logdata` (object, nested values allowed), plus optional `reported_dst_host`. Missing fields are filled with the same defaults `sanitizeLog()` uses (`""`, `-1`, `1001`, `{}`).
- **Connection lifecycle**: `SocketJSONHandler` keeps its socket open and may stay silent for hours (`retryStart = 0`, keep-alive enabled). Idle timeouts therefore apply only to a **stalled partial line**, never to a quiet but healthy connection.
- **Redis layout preserved**: `incident:<kind>:<src_host>:<ts>`, `incidents` (ZSET, score = created), `device:<sha256[:12]>`, `scan:host:…`, `scan:network:…:targets`, `logs`, `whitelist-ips:*`, `console-setting:*`. Incident hash fields preserved (`events_list` CSV of epochs, `events_count`, `acknowledged`, `notified`, `updated`, `description`, `created`, `logdata` JSON string).
- **Behavioural defaults preserved**: 60 s global incident horizon, host-portscan 5 packets / 50 s, network-portscan 2 targets / 3600 s, per-logtype `*.incident_horizon` overrides.

Note: the Redis layout is internal to the correlator; `opencanaryd` never talks to Redis. Keeping the keys protects legacy dashboards and upgrade continuity, not the honeypot protocol.

### Deliberate removals

Twisted, `zope.interface`, `simplejson`, `PyNaCl` (replaced by `hashlib.sha256`), `pkg_resources`, `mandrill` (deprecated client), `twilio==4.4.0`, `bin/` shell script, `setup.py`, `requirements.txt`.

### Dependencies

Runtime: `pydantic`, `pydantic-settings`, `redis`, `httpx`, `aiosmtplib`.
Dev: `pytest`, `pytest-asyncio`, `pytest-cov`, `fakeredis`, `mypy`, `ruff`.
No ORM/SQLAlchemy in this phase — no relational data is in scope; noted as a future optional plugin.

### Validation policy (why compatibility does not regress)

| Risk | Mitigation |
|---|---|
| `src_host` empty string or hostname | accept bounded `str`, not `IPvAnyAddress` |
| `src_port` / `dst_port` = `-1` | allow `-1…65535` |
| Unknown/new `logtype` | accept any int, audit `event_unrouted`, no incident |
| Nested/heterogeneous `logdata` | `dict[str, Any]` + depth/size limits, `extra="allow"` |
| `[ERR] '…'` non-JSON lines | detect, audit, keep connection |
| Silent long-lived connections | idle timeout only on partial-line stalls |
| Unparsable `local_time` | fall back to receipt time + audit |
| Oversized lines | configurable cap, default 64 KiB (legacy was 16 KiB) |

- Compatibility test passes: payload produced by the exact `opencanary` `makePickle()` implementation is accepted and yields a legacy-shaped incident hash.

**Functional acceptance (`docs/validation.md`)**
- `docker compose up` → JSON `startup` audit record; Redis reachable. Status: **met on Docker Desktop 29.9.2** (2026-10-24): fresh build, both services `healthy`, `receiver_started`/`startup`/`incident_created` audit records, uid 10001, read-only root, `/healthz` with Redis, and a graceful `docker stop` ending in `receiver_stopped`/`shutdown`.
- Sending `{"logtype": 2000, "src_host": "10.0.0.5", "src_port": 4444, "dst_host": "10.0.0.2", "dst_port": 21, "node_id": "canary-1", "local_time": "2026-10-24 10:00:00.000000", "logdata": {"USERNAME": "admin", "PASSWORD": "x"}}` + `\n` on TCP 1514 creates exactly one `incident:ftplogin:10.0.0.5:<ts>`, one `incidents` member, and one delivery per configured channel in the legacy report format.
- A second event from the same host within 60 s that differs in any field → `events_count = 2`, no second notification. Status: **covered end to end** by `test_full_stack_ingests_correlates_and_notifies` (two events differing only by `src_port`) and by `test_distinct_events_merge_into_one_incident` on a real Redis. A **byte-identical** event inside `OCC_DEDUP_TTL` (default 60 s) is not merged at all: the fingerprint cache drops it, it is audited as `event_deduplicated`, counted under `result="deduplicated"` in `/metrics`, and `events_count` stays 1 (`test_duplicate_event_is_deduplicated`, `test_duplicate_events_notify_once_across_replicas`). The Python 2 correlator had no such cache, so this is a deliberate new behaviour rather than a regression - documented in the README, and `OCC_DEDUP_TTL=0` restores the old counting for operators who want retransmissions merged.
- Five SYN events to five ports within 50 s → `scans.host_portscan`; two nodes scanning the same `src_host:dst_port` within 1 h → `scans.network_portscan`. Status: **covered end to end** by `test_host_portscan_through_the_wire` and `test_network_portscan_through_the_wire` (2026-10-24), through the real `SocketJSONHandler` socket and the default thresholds.
- Container restart loses no acknowledged state; a second replica produces no duplicate alerts. Status: **met**. `docker compose restart correlator` came back healthy with the incident hash and the Redis volume intact (`events_count = 1`, `docs/validation.md`), and since no acknowledged state lives outside Redis a restarted replica is correct by construction rather than by luck. The replica half is covered on a real server: `test_duplicate_events_notify_once_across_replicas` sends 50 concurrent identical events through two engines and asserts one incident key, `events_count = 1` and exactly one delivery; `test_redis_atomicity::test_duplicate_events_across_replicas_notify_once` pins the same guarantee at the store level.
- Audit JSON parses line-by-line, every record has the five mandatory fields, no plaintext passwords from `logdata`. Status: **met**. `test_audit_event_requires_mandatory_fields` and `test_emit_writes_one_json_line_with_required_fields` pin the record shape, the end-to-end run asserts all five keys on every record it produced, and `test_emit_writes_one_json_line_with_required_fields` additionally asserts that a `PASSWORD` in `details` is written as `***` and a multi-line value flattened, so a leaked credential cannot reach the audit stream.

**Performance sanity (measured, reported as numbers)**
- 10,000 events over one connection: **a recorded range, not a gate** (rewritten 2026-10-25). The earlier "< 10 s" form was met by one 2.6 s run and is withdrawn, because the same commit has since measured **5.145 s**, **12.040 s**, **12.539 s** (1 host, 1 lane), **11.369 s** (100 hosts, 8 lanes) and 11.1 s through Docker Desktop, all against a native `redis-server` on the runner. The spread is CPU steal on a shared runner plus an 8-lane event loop competing with itself, not the code, so a wall-clock threshold cannot be defended in either direction. What is checked per run is what the tool asserts: `accepted + dropped == events` with `rejected == 0`, 10 000 events over one connection, no unbounded queue growth. The elapsed seconds are published in the benchmark job summary as numbers to compare between builds. `docs/validation.md` carries the table.
- RSS < 250 MB: **met by measurement** (2026-10-25). `tools/bench_ingest.py` reports `rss_mib` through `opencanary_correlator.utils.memory` (`/proc/self/status` on Linux, `getrusage` elsewhere, `GetProcessMemoryInfo` on Windows - the earlier probe declared `PROCESS_MEMORY_COUNTERS` with `c_ulong` fields, which is 4 bytes on 64-bit Windows, so the call failed and answered nothing). Peak **70.9 MiB** for 10 000 events over 100 hosts and **70.0 MiB** for 10 000 events into a single incident, from a 48 MiB baseline: the queue and the connection pools set the footprint, not the incident size. Details in `docs/validation.md`.
- Server p99 latency increase < 2 ms during the run: **measured, and met** (2026-10-25). `redis-cli --latency` reports min/max/avg and no percentile, so the criterion is measured by `tools/latency_probe.py`, a second client that pings every 5 ms from its own process while both 10 000-event runs execute. On the native runner: idle p99 **305.4 µs** (n = 995, p50 214.2 µs) against **277.4 µs** under load (n = 5 244, p50 193.2 µs), a change of **−28 µs**. Through Docker Desktop's NAT the same shape appears with both figures inflated by the proxy (696.9 → 506.1 µs, n = 995 / 2 761). The negative direction is the honest reading: the difference is below the resolution of the measurement, which is what "no measurable degradation" looks like. Rendered in the benchmark job summary on every run.
